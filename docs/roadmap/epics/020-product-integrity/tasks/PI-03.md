## Acceptance Criteria

- [x] Write a compact product and accounting contract for marking exactly two
  imported rows as one real transaction, choosing a canonical record, displaying
  the relationship, and reversing the decision.
- [x] Define eligibility and validation for same/different accounts, signs,
  currencies, pending/posted state, already-related rows, transfer pairs, refund
  matches, and source changes or deletion without silently guessing intent.
- [x] Specify which record contributes to spending, income, recurring detection,
  counts, category analytics, Sankey, search/review queues, and historical reports
  before marking, after marking, and after reversal.
- [x] Preserve both imported source records and distinguish manual economic
  duplication from provider replay/pending-to-posted identity handling.
- [x] Define durability across sync, relink/fingerprint reapplication, provider
  modification/removal, and orphan cleanup, including what becomes invalid and how
  the user is informed.
- [x] Define a minimal selection/confirmation/reversal experience for desktop and
  mobile, with language that does not imply automatic fraud or duplicate detection.
- [x] Provide a small hand-calculated fixture and an implementation/test handoff for
  PI-04 and PI-05. Record any material unresolved product decision rather than
  embedding it silently in schema work.

## Technical Context

There is no current duplicate relationship. `Transaction` has provider identity and
content-fingerprint fields; `TransactionAnnotation` stores notes/review/refund data;
`TransferPair` is the existing example of a structured reversible relationship.
Transactions already support multi-selection and a batch-annotation sheet in
`frontend/src/routes/transactions.tsx`, but freeform notes or a shared annotation
must not become the duplicate source of truth. Read CF-02's identity decisions and
CF-05's sync lifecycle before defining invalidation behavior.

Suggested role: product/accounting designer with backend maintainer review. The
accepted [duplicate-correction contract](../artifacts/PI-03-duplicate-contract.md)
is the handoff for PI-15, PI-04, PI-17, and PI-05.
