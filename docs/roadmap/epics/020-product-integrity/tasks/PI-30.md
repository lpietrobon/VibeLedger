## Acceptance Criteria

- [ ] Before changing production reconciliation, add a frozen, deterministic test
  contract that reproduces the confirmed-route gap using wholly synthetic
  accounts, descriptions, dates, amounts, categories, and identifiers. Do not
  copy, aggregate, hash, or otherwise encode private ledger values in Git.
- [ ] Pin the positive shape: an exact, mutually unique, equal-and-opposite pair
  spans active linked accounts; one leg has structured provider payment evidence;
  the counterpart lacks coherent structured transfer evidence; and prior manual
  confirmations establish the same directed account route with a stable signature
  on one leg while the other leg's description changes only in bounded numeric
  tokens. The new pair should be automatically confirmed with auditable evidence.
- [ ] Prove lifecycle behavior through the existing detection entry point: a
  previously created review candidate is rebuilt and promoted during redetection,
  and the same promotion occurs after a successful refresh with no imported row
  delta. The test must fail at the diagnosed evidence decision, not because the
  fixture bypasses sync, matching, or active-account eligibility.
- [ ] Preserve the mutually unique best-match requirement. Add competitors on
  both sides and permute insertion order to prove that ambiguity remains in review
  and no decision depends on database IDs or iteration order.
- [ ] Prove that account-route history alone is insufficient. No automatic
  confirmation may occur when both descriptions are unstable, the stable leg no
  longer matches, the numeric variation changes non-numeric meaning, either leg
  lacks payment/transfer corroboration, or the candidate uses a different route.
- [ ] Add adversarial numeric-token controls so normalization cannot collapse
  unrelated counterparties, account references, dates, or arbitrary descriptions
  into one trusted signature. Prefer an explicit route-evidence representation
  over broad digit stripping or fuzzy string similarity.
- [ ] Preserve rejection, reversal, and source-change safety: a rejected pair is
  not recreated; a manual confirmation is not overwritten; and an automatically
  confirmed pair reopens or is invalidated when the evidence that qualified it
  changes.
- [ ] Prove shared accounting behavior: only the automatically confirmed synthetic
  movement is excluded from income and spending; weak candidates and unmatched
  rows remain counted and reviewable in both Activity and Sankey responses.
- [ ] Record the red command, failing assertions, fixture rationale, privacy check,
  and frozen contract under
  `artifacts/PI-30-variable-description-route-tdd.md`. A follow-up implementation
  may repair product code or add separate tests but may not weaken or edit this
  accepted oracle without escalation.

## Technical Context

The current classifier in `app/services/transfer_detector.py` automatically
confirms a mutually unique pair when both legs have coherent structured provider
evidence or when an earlier confirmed pair has the same directed accounts and
exact normalized descriptions on both legs. Live review established that refresh
and candidate rebuilding are working, but exact two-sided description equality can
abstain on a recurring route when one provider description contains changing
numeric tokens and the counterpart provider classification is incomplete.

This task must define a narrow deterministic route-evidence contract before any
normalization changes. The contract should retain PI-27's precision boundary:
amount/date proximity, account types, one transfer-looking label, a shared account
route, or free-form wording alone never justifies automatic exclusion. Do not
expand into fuzzy matching, probabilistic scoring, FX/fee inference, or many-to-many
reconciliation.

Existing contracts in `tests/test_pi19_card_payment_tdd.py`,
`tests/test_pi27_generic_transfer_reconciliation_tdd.py`,
`tests/test_pi28_generic_transfer_implementation.py`, and
`tests/test_transfer_detector.py` remain unchanged.

Suggested role: accounting/test engineer; the contract was reviewed and frozen,
then implemented in the same scoped PI-30 delivery at the user's direction.
