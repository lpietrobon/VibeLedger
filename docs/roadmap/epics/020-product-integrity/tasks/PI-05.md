## Acceptance Criteria

- [ ] Selecting exactly two eligible Activity rows offers an explicit “Mark as
  duplicates” action and a confirmation step that identifies the canonical record
  and explains the effect on totals.
- [ ] Invalid selections are disabled or rejected with specific guidance; the UI
  never infers a duplicate solely from matching amount, date, merchant, or name.
- [ ] Canonical and duplicate rows remain visible with understandable relationship
  state in Activity and transaction detail, and either record can lead to the other.
- [ ] The user can reverse the relationship; success/error feedback is visible,
  survives refresh, and all affected ledger queries are invalidated.
- [ ] The workflow is keyboard operable and usable in both the desktop table and
  mobile row layout without turning the existing batch editor into an ambiguous
  source of truth.
- [ ] A fixture with two true duplicate rows and a separate legitimate same-value
  purchase demonstrates the exact before/after/reversed rows and aggregate changes.
- [ ] Add focused React interaction/API-client tests and complete a synthetic-data
  walkthrough; run frontend tests, typecheck, build, and PI-04 backend regressions.
- [ ] Make PI-17's accepted interaction cases pass unchanged; escalate rather than
  modifying those cases if they no longer represent the approved product contract.

## Technical Context

`frontend/src/routes/transactions.tsx` already maintains `selectedIds` across mobile
and desktop and opens `BatchAnnotationSheet` for general edits. Add a distinct
relationship action rather than encoding it in batch notes. `TransactionRow`, the
desktop status cell, `AnnotationSheet`, API types/client, and
`invalidateLedger()` are likely integration points. Follow the product language and
eligibility rules accepted in PI-03.

Suggested role: frontend/product engineer, independently reviewed against the
accounting fixture.
