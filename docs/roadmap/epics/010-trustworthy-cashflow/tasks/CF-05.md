## Acceptance Criteria

- [x] Replaying the same provider record or sync page does not create another economic transaction or change totals.
- [x] Pending-to-posted transitions leave one posted transaction in realized reporting and preserve valid user corrections.
- [x] Provider changes to posting date, amount, description, or removal update reports and invalidate stale derived matches as appropriate.
- [x] Failed or interrupted batches can be retried without partial duplication, skipped history, or lost user decisions; verify cursor and transaction atomicity.
- [x] Deletion and relinking do not leave orphan annotations, transfer/refund relationships, or rejection records attached to unrelated transactions.
- [x] Adding a linked account or older history makes counterpart reconciliation possible without requiring historical reports to be rebuilt by hand.
- [x] Assess duplicate account coverage from relinking/repeated linking; prevent silently presenting double-covered totals as reliable, using the smallest supported correction path.
- [x] Add focused regression tests and document actual provider/history/currency limitations. Do not claim Venmo support from synthetic examples alone.

## Technical Context

Suggested role: ingestion/backend engineer. Inspect `sync_service.py`,
`plaid_client.py`, `txn_fingerprint.py`, model constraints, schema patches, and
item-removal paths. Distinct same-amount purchases are not import duplicates.
Avoid destructive cleanup against real data and avoid matching account identities
by weak fields alone. Any migration must preserve annotations and be repeatable.

Coordinate lifecycle interfaces with CF-06 and CF-07; assign ownership before
editing shared routes/schema files. New provider integrations are separate scope.
