## Acceptance Criteria

- [ ] A verifier other than the implementer evaluates an identified integrated commit using expected totals derived independently from production calculation code.
- [ ] Verify salary, card purchases/repayments, checking transfers, payment-account funding/spending, merchant refunds, an external counterparty, and a linked partner/investment counterparty.
- [ ] Prove confirmed internal movements do not change expense/income and each external economic event contributes exactly as specified; verify net equals income minus expenses under CF-02's convention.
- [ ] Challenge equal-amount unrelated rows, competing transfer matches, actual repeated charges, import replay, pending-to-posted changes, and invalid currency/account combinations.
- [ ] Exercise source modifications/removals, failed-sync retry, new account/history arrival, manual corrections, and re-detection after rejection; verify historical recomputation and annotation integrity.
- [ ] Compare aggregate APIs, category totals, effective SQL/dashboard queries, and full paginated drill-down evidence on the same scenarios and dates.
- [ ] Record commands, expected/actual results, tested commit, and reproducible failures. Fixes go back to the responsible task or a new defect task; reverify the changed commit.
- [ ] No unresolved defect that can silently misstate scoped cashflow remains at acceptance. Explicit unsupported cases are documented and not presented as covered.

## Technical Context

Suggested role: independent accounting QA/verifier. Use CF-02's worked examples
as the initial oracle, then add adversarial cases rather than merely rerunning
the implementer's tests. Reuse the test harness, but do not call production
functions to generate expected answers. Use synthetic data only.

The verifier reports evidence and gates completion; this is not a second feature
implementation pass. If rework changes task scope, use the supersession pattern.
