## Acceptance Criteria

- [x] Only established internal movements between linked accounts are excluded from realized income and expense; uncertain candidates remain counted and reviewable.
- [x] Verify checking-to-checking, linked card repayment, and linked payment-account funding without relying on account ownership or a fixed account-type whitelist.
- [x] Same-size unrelated transactions and ambiguous competing matches cannot silently hide real expenses. Prevent a transaction from belonging to incompatible pairs.
- [x] Matching respects opposite direction, account identity, posting-date tolerance, and currency; never infer exchange conversion from matching nominal amounts.
- [x] Confirm, reject/unpair, and manual pairing have explicit reversible effects. Rejected candidates stay rejected after detection or sync unless evidence/user action legitimately changes the decision.
- [x] Source changes or deletion invalidate stale relationships; new counterpart history can reconcile past activity and update reports.
- [x] API validation rejects invalid pairs with useful errors. Preserve enough paired-transaction evidence for review and drill-down.
- [x] Add tests for the positive cases, false-positive collisions, competing matches, repeated detection, and persisted corrections.

### 2026-09-06 — acceptance closure

Automatic candidates now require reciprocal, sole closest matches. Every automatic,
manual, and confirmed pair shares one validation boundary: posted nonzero opposite
amounts, distinct linked accounts, outflow before inflow within the permitted
posting gap, and **known equal currencies**. Unknown or mismatched currencies stay
ordinary counted activity; they never become a nominal exchange-rate inference.

Material source changes clear affected rejections as well as stale pairs, and added
or modified history clears only unconfirmed automatic candidates before conservative
re-detection. Confirmed/manual decisions and unchanged rejections remain durable.
Transfer evidence now includes each leg's currency for review. Regressions cover
checking/card/payment-account cases, symmetric collisions, invalid API pairs,
currency evidence, source correction, and later-arriving counterpart history.
