## Acceptance Criteria

- [ ] Replace the current all-or-nothing Sankey fallback: a period containing a category whose net spending is negative still renders a faithful cashflow allocation in both React and Streamlit.
- [ ] For each effective category, compute `net_category_amount = posted charges + posted refund credits` using the established CF-07 accounting scope. Confirmed transfers and pending rows remain excluded; refund credits remain tied to their effective purchase category where existing rules provide that link.
- [ ] Split the grouped result into positive net spending and residual credits. Positive values remain spending flows. The absolute value of negative categories is presented as **Net refund credits**, meaning only credits left after netting refunds against spending in the same category—not income and not total refund volume.
- [ ] Label the refund node or section **Net refund credits** and include concise explanatory text: “Refunds remaining after offsetting spending in the same category. Not income.” A refund must never be included in the displayed income total or income-source breakdown.
- [ ] Keep the diagram arithmetically balanced. Let `P` be the sum of positive net category amounts, `C` the absolute sum of negative net category amounts, and `I` reported income. Preserve `net_spend = P - C`, `savings = max(I + C - P, 0)`, and `deficit = max(P - I - C, 0)`. Every visible flow and displayed total must reconcile to these identities.
- [ ] Category and bucket expansion remains truthful when positive and negative categories share a bucket: positive category links sum to the positive spending flow, while residual negative categories appear under Net refund credits and are not silently dropped, clipped to zero, or forced into a negative-width link.
- [ ] Handle refund-only periods, no-refund periods, net-zero categories, net-negative total spending, zero income, and spending greater than income without disabling the entire visualization or producing invalid Sankey link values.
- [ ] Preserve the current period controls, accessible chart/section labels, loading/error behavior, and responsive layout. The UI should remain understandable without requiring the user to know Sankey limitations.
- [ ] Implement test-first. Commit or record the failing backend and frontend cases before the fix, then make them pass. Add focused API/accounting tests, React rendering/graph tests, and Streamlit coverage; record red/green commands and results in this task’s Execution Log.

## Technical Context

Suggested role: full-stack product engineer. Read the epic spirit and CF-02
accounting contract before changing code. The server remains the sole owner of
money calculations; do not recompute refunds from raw transactions in React.

Start with `analytics_cashflow_sankey` in `app/api/routes.py`. Its category query
already sums the shared `expense_amount()` expression, so preserve that definition
and expose a complete grouped result instead of setting `sankey_supported` false
whenever one category is negative. A small explicit response contract is preferred:

- positive net spending grouped into drawable buckets/categories;
- `net_refund_credits`, the positive magnitude `C`;
- `net_refund_credit_categories`, with positive magnitudes and category names;
- `total_spend`, which remains signed net spend `P - C`;
- enough totals for the client to verify/display reconciliation without deriving
  transaction-level accounting.

In React, update the API types/client and `SankeyChart`. A balanced layout may use
Income, Net refund credits, and Deficit funding as distinct sources feeding an
explicit available-cash/allocation node before positive spending buckets and
Savings. Do not route refund credits through an Income node. If a simpler companion
credit section is clearer, it is acceptable only if the Sankey and credit section
together expose all `P`, `C`, net-spend, savings, and deficit values without a
contradiction. Mirror the accounting meaning in `pages/3_Cashflow_Sankey.py`; visual
parity is not required.

TDD minimum scenarios should include: CF-02 February (`P=90`, `C=120`, net spend
`-30`, income `3000`, savings `3030`); positive and negative categories sharing one
bucket; a refund smaller than charges in its category; a refund-only category;
no refunds; and confirmed-transfer/pending-row exclusion. Tests should fail for the
old disabled-chart behavior and pass only when all visible flows are non-negative
and reconcile.
